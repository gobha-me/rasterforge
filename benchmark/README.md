# RasterForge benchmark harness

This developer-only executable records scalar decode, fit, compositing, and
external-copy costs for RF-05d. It is workload evidence, not a correctness test
or a performance gate: CTest never registers it, no timing threshold can fail a
build, and consumers do not build or install it.

The first committed result set is the
[2026-08-26 RF-05d scalar baseline](../docs/benchmarks/rf-05d-2026-08-26.md).

## Workload provenance

The harness creates every source and encoded PNG in memory before timing. The
RGBA pattern is deterministic and includes translucent pixels; PNG generation
uses the linked zlib at `Z_BEST_SPEED`. Generated bytes, setup allocations, and
temporary-budget probing are excluded from timing.

| Name | Extent | Provenance |
| --- | ---: | --- |
| `tiny_1x1` | 1x1 | Lower-bound overhead case; not a consumer throughput claim. |
| `termforge_320x180` | 320x180 | The straight-alpha software frame requested by the RF-05d issue for TermForge's 30 FPS game/display path. |
| `venice_proxy_768x1024` | 768x1024 | Upper proxy from Venice's documented portrait generation example. AIForge has not established a production display extent, so this is not labeled as one. |

Every extent runs PNG decode, same-extent nearest and triangle fit, solid and
image source-over compositing, and the example-owned external RGBA copy. Two
additional cases fit the 768x1024 proxy into 320x180 with cover geometry and
both filters.

## Reproduce a Release run

```bash
cmake -S . -B build-benchmark \
  -DCMAKE_BUILD_TYPE=Release \
  -Drasterforge_BUILD_BIN=OFF \
  -Drasterforge_TESTS=OFF \
  -Drasterforge_FUZZERS=OFF \
  -Drasterforge_INSTALL=OFF
cmake --build build-benchmark --parallel --target rasterforge-benchmark

build-benchmark/benchmark/rasterforge-benchmark \
  --samples 20 --sample-ms 25 --format table
build-benchmark/benchmark/rasterforge-benchmark \
  --samples 20 --sample-ms 25 --format csv
```

Capture the source and machine beside published results:

```bash
git rev-parse HEAD
c++ --version
cmake --version
uname -a
lscpu
```

`--samples` controls the number of recorded samples. Each sample batches enough
operations to meet `--sample-ms`; the reported time is per operation. Both
arguments require positive 32-bit integers. Unknown arguments and unsupported
formats return a nonzero status.

## Columns and limitations

- `median_us` and `p95_us` are per-operation steady-clock wall times after one
  warmup and an untimed batch calibration.
- `operations_per_second`, `megapixels_per_second`, and
  `output_mib_per_second` are derived from the median. Output MiB/s normalizes
  the four-byte destination payload; it is not a claim about actual memory-bus
  traffic.
- `temporary_floor_bytes` is the smallest inclusive
  `max_temporary_bytes` value that lets the operation succeed. It describes
  RasterForge's resource contract, not process RSS.
- `cpp_allocation_calls`, `cpp_allocated_bytes`, and
  `cpp_peak_outstanding_bytes` observe ordinary C++ `new`/`new[]` calls made by
  one operation. Codec-owned C allocations and over-aligned allocations are not
  visible. ThreadSanitizer owns the global allocation operators, so TSan builds
  report these fields as `n/a`.
- Encoded bytes and output checksums remain visible so a run cannot silently
  change input size or let the optimizer discard operation results.

Compare results only when compiler, build type, source revision, zlib version,
and machine metadata are recorded. Open optimization work only for a measured
consumer bottleneck with an explicit workload and target.
